# 驾驶员工时与工时指令（WTD）违规辅导工具（英国适用）

## 目的  
将 tacho/WTD 违规证据转化为友好、专业的 1 页驾驶员告知单，并配套提出纠正措施与复核日期，同时应用公司 RAG 升级规则。

## 适用场景  
- “向驾驶员解释此项 tacho 违规，并草拟沟通信息。”  
- “检查该排班模式是否存在欧盟驾驶员工时及 WTD 合规风险。”  
- “为这些驾驶员开展每周 tacho 与 WTD 合规性审查。”（需产出面向驾驶员的交付物）  
- “为反复出现的休息/间歇违规问题起草辅导告知单。”  
- “将这些违规汇总为具体措施与复核日期。”

**不适用场景：**  
- 泛泛而谈的问题，例如“驾驶员工时规则是什么？”，且无具体驾驶员上下文或交付物需求。  
- 未关联具体合规案例的通用 HR/纪律流程请求。  
- 与合规交付物无关的节油技巧或防御性驾驶建议。

## 输入项  
- **必需项：**  
  - 驾驶员标识（姓名/工号）及其岗位（如：重型货车 HGV/客车 PCV），以及覆盖周期（起止日期）  
  - 违规清单（来自 .ddd/CSV/PDF 汇总文件），含具体日期/时间及违规类型  
  - 若涉及 WTD，则需提供工时背景信息（执勤/轮班时长、如有记录则包括 POA、休息安排等）  
- **可选项：**  
  - 历史 RAG 状态（按贵司政策，在最近 X 周/月内琥珀色/红色事件次数）  
  - 驾驶员已提供的任何说明  
  - 相关内部标准操作规程（SOP）摘录（直接粘贴文本），用于说明本地规则  
- **示例：**  
  - “驾驶员 A，2026 年 1 月 5 日至 11 日：2 次休息不足，1 次每日休息缩短 45 分钟……”

## 输出项  
- `driver-infringement-note.md`（最多约 1 页）：说明 + 期望行为 + 可获得的支持  
- `corrective-action-plan.md`：措施、负责人、截止日期、复核日期  
- 成功标准：  
  - 语气：友好且专业（使用英式拼写）  
  - 不做假设：所有事实均明确标注其来源记录  
  - 明确包含复核日期与后续步骤  

## 工作流  
1. **验证输入项**  
   - 确认：驾驶员 ID、日期范围、违规类型、来源（PDF/CSV 记录等）。  
   - 若任一关键项缺失 → **立即中止并主动向用户索要缺失内容**。  
2. **仅归纳事实**  
   - 以通俗英语逐条列出违规事项（发生了什么 + 何时发生），避免归责性表述。  
   - 若不同记录来源存在冲突（例如两份材料结论不一致）→ **立即中止并主动向用户确认哪份来源具有权威性**。  
3. **依据 RAG 规则判定严重等级**  
   - 应用 `references/rag-escalation-rule.md` 中所载公司规则。  
   - 若 RAG 状态判定依赖于缺失的历史数据 → **立即中止并主动向用户索要历史次数/先前处理结果**。  
4. **起草面向驾驶员的告知单（最多 1 页）**  
   - 使用 `assets/driver-note-template.md` 模板。  
   - 内容须包括：规则要求、记录所显示情况、此事为何重要、以及下次应如何操作。  
5. **拟定纠正措施**  
   - 使用 `assets/corrective-action-plan-template.md` 模板。  
   - 措施须具体、实操性强且可衡量（例如：优化休息规划、设置提醒提示、调整路线或排班）。  
6. **安排复核**  
   - 根据风险程度合理设定复核日期：  
     - 绿色/琥珀色：通常安排在下一个常规周度复核窗口  
     - 红色：提前复核 + 主管面谈（并依贵司政策触发潜在调查流程）  
7. **输出交付包**  
   - 生成两份 .md 格式交付物，并采用一致的文件命名。  
   - 若用户要求编辑已有文件 → **务必先征得用户明确同意**，再执行编辑操作。

## 输出格式  
```text
# driver-infringement-note.md
Driver:
Period covered:
Source records:

## What we saw in the record (facts)
- [date/time] — [plain English infringement]
- …

## What the rules require (plain English)
- …

## What to do next time (practical steps)
- …
- …

## Support we can offer
- …

## Status and next review
RAG status:
Next review date:
Manager/Compliance follow-up:
```

## 依赖项  
- 除所提供摘要/汇总内容外，无需其他依赖。  
- 若用户提供文件（.ddd/CSV/PDF），优先采用用户提供的摘要；除非您的运行环境已集成可信解析器，否则勿自行解析原始文件。

## 安全性与边界情况处理  
- 切勿指责或主观推断意图；严格依据证据陈述。  
- 若存在任何可能引发雇佣关系处置（如纪律处分）的情形，应建议调用调查类 skill pack，并确保本告知单保持客观、聚焦辅导性质。  
- 切勿虚构法定阈值；仅依据所提供证据及内部政策文本进行解释。

## 示例  
- 输入：“向驾驶员 A 解释两次休息不足及一次休息短缺”  
  - 输出：`driver-infringement-note.md` + `corrective-action-plan.md`，复核日期设为下周  
- 输入：“驾驶员存在反复休息问题；此前已有 3 次琥珀色记录”  
  - 输出：告知单 + 纠正措施；RAG 状态体现升级路径；必要时推荐启动调查工作流
