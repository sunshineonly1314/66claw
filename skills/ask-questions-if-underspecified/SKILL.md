# 若需求不明确则提问

## 目标

提出最少数量的关键澄清问题，以避免执行错误的工作；在所有关键问题得到解答（或用户明确批准按既定假设继续推进）之前，不得开始实施。

## 工作流程

### 1) 判断请求是否不明确

若在探索如何执行该任务的过程中，以下一项或多项内容尚不清晰，则视为需求不明确：

- 明确目标（哪些内容应变更、哪些应保持不变）；  
- 明确定义“完成”标准（验收条件、示例、边界情况）；  
- 明确范围（涉及/不涉及的文件/组件/用户）；  
- 明确约束（兼容性、性能、风格、依赖、时间）；  
- 明确运行环境（语言/运行时版本、操作系统、构建/测试工具）；  
- 明确安全性与可逆性（数据迁移、上线/回滚策略、风险）。

若存在多种合理解释，则默认视为需求不明确。

### 2) 优先提出关键问题（保持精简）

首次提问应限制在 1–5 个问题以内。优先选择能一次性排除整类工作路径的问题。

确保问题易于回答：

- 注重可扫读性（问题简短、编号清晰；避免大段文字）；  
- 尽可能提供多选选项；  
- 在合适时建议合理默认值（明确标注为默认/推荐选项；在列表中加粗推荐项，或在代码块上方添加加粗的“Recommended”行，并在代码块内也标注默认项）；  
- 提供快捷响应路径（例如，回复 `defaults` 即表示接受全部推荐/默认选项）；  
- 在有帮助时提供低门槛的“不确定”选项（例如，“不确定 — 使用默认值”）；  
- 若有助于降低沟通成本，可将“必须知晓”与“了解即可”两类问题分开；  
- 结构化选项，使用户能以简洁方式做出决策（例如，`1b 2a 3c`）；并在确认时用平实语言复述所选选项。

### 3) 在获得关键答案前暂停行动

在关键答案到达前：

- 不得运行命令、编辑文件，或制定依赖未知信息的详细计划；  
- 仅允许执行明确标识、低风险的探索性操作（例如，检查仓库结构、阅读相关配置文件），且该操作不得将你锁定于某一方向。

若用户明确要求你在无答案情况下继续推进：

- 以编号列表形式陈述你的全部假设；  
- 请求用户确认；仅在其确认或修正后方可继续。

### 4) 确认理解无误，再正式推进

一旦获得全部答案，请用 1–3 句话复述需求要点（含关键约束及成功标准），随后启动工作。

## 提问模板

- “开始前我需要确认：(1) ……，(2) ……，(3) ……。若你对 (2) 无特别要求，我将默认采用……。”  
- “应选择以下哪一项？A) …… B) …… C) ……（请择一）”  
- “你认为什么是‘完成’？例如：……”  
- “是否有必须遵守的约束（版本、性能、风格、依赖）？若无，我将遵循当前项目的既有默认规范。”  
- 使用编号问题 + 字母选项 + 清晰的回复格式

**推荐**
```text
1) Scope?
   a) Minimal change (default)
   b) Refactor while touching the area
   c) Not sure - use default

2) Compatibility target?
   a) Current project defaults (default)
   b) Also support older versions: <specify>
   c) Not sure - use default

Reply with: defaults (or 1a 2a)
```

## 反模式（应避免的做法）

- 不要提出可通过快速、低风险的探索性阅读（如查阅配置、已有模式、文档）自行解答的问题。  
- 若紧缩的多选题或是非题能更快消除歧义，就不要提开放式问题。
